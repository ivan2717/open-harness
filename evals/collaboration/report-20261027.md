# Open Harness 主子 agent 验收报告

日期：2026-10-27（Asia/Shanghai）。测试对象为当前工作区编译的生产 API、适配器、执行循环、文件工具及协作机制。本次没有重新打包或重启日常桌面应用。

## 真实业务对照

使用已有配置中的官方 OpenAI `gpt-6-luna`，Responses 协议、medium 思考、1,050,000 上下文、8,192 输出上限。保险库只读，密钥仅在内存和发往本机配置接口的请求中使用。没有使用模拟模型代替这一组测试。

材料是独立生成的 6 个订单、8 行付款、4 行退款及规则；包含重复付款、孤立付款、孤立退款、失败／取消付款、未付款、部分付款、待结算退款。每次使用全新工作区和会话，同一模型设置。标准答案在评分器中，不在模型能读取的测试目录或提示词中。

三种模式各执行三次，顺序轮换：单 agent／自动／指定协作，指定协作／单 agent／自动，自动／指定协作／单 agent。每例最多 240 秒、每 agent 每轮 24 个模型步骤、最多 2 个并发子任务；均未触发这些验收护栏。它们不改变产品默认运行限制。

九次合计已记录输入 **519,896**、输出 **39,180** tokens、**87** 次模型响应。这是主子任务全部已记录响应之和，不是完整账单；缓存计价、失败／重试和可能未纳入的 Wiki、摘要调用不可据此推算费用。耗时包含模型、工具、运行时及轮询。

所有结构化结果都正确：订单 700、有效付款 475、生效退款 50、净回款 425、退款前欠款 225；逐订单金额、付款／退款依据及七类异常也全部正确。四份源文件的最终哈希每次都保持一致。

每次自动评分 32/32，但其中 2 项只检验报告存在性和文件名引用，不能判定全文正确。逐份独立复核发现九份报告的业务结论一致，一份存在轻微措辞问题：delegated-3 称全部有效付款“金额与订单匹配”，但 P204 是 O105 的部分付款；同文的数字和部分付款分类仍正确。原产物没有事后修正。

**这道小型任务中，指定多 agent 没有提高结果正确率，平均耗时约为单 agent 的 1.71 倍，已观测 token 约为 4.73 倍。**自动模式三次都没有分工，这是这个任务中合理的行为。样本很小且只有一个业务题，不能据此推导大规模、多领域任务的收益或统计显著性。

## 协作过程质量

三个指定协作任务均真正创建两个子任务，分别读取源材料、回传金额／异常结果；主任务自己也读取材料，在两份实质结果送达后写文件，并回读交付。公开记录支持真实并发存活和结果回传；不是仅在回答里口头扮演多个角色。

但九次基础对账都没有实际执行计算脚本，因此正确结果不能证明主 agent 用独立程序复算过，也不能证明它能识别一个故意给错结论的子 agent。具体事件序号见独立评审记录。

发现并保留以下执行问题：

1. **协作等待误报。** delegated-1 的三次 `agent_control wait` 分别收到了金额结果、完成消息、异常结果，第三次仍触发重复调用提醒。重复检测只对命令管理作特殊处理，没有识别协作消息进展。这是 harness 的提示误报；没有中止任务。
2. **三次重复参数拒绝。** delegated-1 一次、delegated-3 两次 spawn 参数同时包含两个 `write_paths`。系统在创建前拒绝，模型重试修正后成功。Schema 只声明一次，源码读取链原样接收提供方最终参数，未发现本地拼接重复的证据；没有原始 wire 抓包，不能再细分模型生成或服务端处理。严格拒绝权限参数重复是合适行为，不能为获得零报错而改成随意覆盖。
3. **不存在的目录探查。** 个别任务在创建 outputs／临时目录前查询它们，得到文件不存在，随后恢复交付。

本轮不修改生产实现，以保持九次基线可比较；等待误报应作为后续修复项。

## 机制验收

独立执行真实运行时配合脚本化模型和本机模拟 MCP：协作 12 项、撤销／恢复 4 项、扩展授权与控制 38 项，合计 **54/54**。

覆盖父子权限和 MCP 继承、可复用授权边界、父会话审批、拒绝与撤回、父停子停、重启不自动重放、持久化结果回传、公开历史分页、文件租约、并发上限及超过 12 步。不能把这些模拟提供方测试计入上述真实业务正确率。

## 压缩后的连续性

另行用同一真实模型测试早期用户状态更正、压缩、子任务回查原始历史和脚本复算。仅在测试配置中把窗口缩为 24,576、输出上限缩为 4,096，确保真实压缩边界可以重现；这不是 1M 容量压测。

**两次均未完成交付，不能算通过。** 首轮在 99.6 秒触及 220,000 已观测 token 护栏；仅放宽护栏后的新会话复验在 233.0 秒触及 450,000 护栏。受在途响应影响，实际记录分别为 232,873 和 454,795 tokens。两次都是 7/16 自动检查通过：四份源文件不变、压缩覆盖更正、创建一个子任务、子任务成功读回父会话更正；最终交付和脚本执行没有完成。

复验暴露了两个优先问题：

1. **写入范围不易正确使用，出错后协作没有恢复。** 主任务给子任务 `write_paths:[".openharness-tmp"]`，把目录当成写入范围；实际协议只支持精确文件。这个尚不存在的路径被当成文件接受，子任务无法创建其下的脚本，父任务接管时又遇到已保留路径的冲突。随后双方反复协调而未解开限制。这不是系统沙箱启动失败：复验没有命令调用或审批记录。
2. **压缩改写了关键标识。** 子任务摘要把真实父 ID 中的 `-43f-1` 写成 `-43-f-1`，之后两次调用使用错误 ID，收到“agent not found”。退款更正 R303→settled 本身保住了，但这说明自然语言摘要不能承担任务标识的唯一来源；关键 ID 应从结构化宿主状态获得。

另有工具契约缺口：`search_run_history` 的 schema 未给出最大 `limit`，执行器却拒绝大于默认 8 的请求；首轮模型传入 10 后失败重试。详细证据及主子事件序号见 [连续性复核](continuity-review-20261027.md)。

这些结果支持“基础读材料与汇总协作可用”，不支持“长任务协作已经可靠”。后续应先修复写入范围的错误反馈与恢复、结构化身份保持、历史工具参数契约及等待误报，再原样重跑；不要只提高预算或删除失败用例。
