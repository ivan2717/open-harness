# DeepSeek 上下文管理实测

测试日期：2026-10-21。请求的模型为 DeepSeek-V4.1-Flash-1017，实际 API
名称为 `deepseek-flash`。这一映射来自
[DeepSeek 官方说明](https://api-docs.deepseek.com/)；
服务器 `/models` 返回名称 `DeepSeek-V4.1-Flash`，没有单独返回不可变的 `1017` 版本号。

结论：本次合成场景中，大窗口适配、连续摘要、用户约束保留、被裁剪内容回查、
摘要失败后的安全处理均通过。测试发现并修复了历史搜索的原文匹配问题，补清了
搜索工具的匹配语义。结果不能替代生产任务的长期可靠性评估。

## 实际接入和预算

测试调用真实 Rust `AgentRuntime`、`CompactingContextManager`、
`ModelContextCompactor` 和 `EventStoreHistoryAccess`，主模型与摘要模型都请求
DeepSeek 官方 HTTPS API。没有用独立模拟器代替运行时，也没有上传仓库源码；
输入全部是生成的合成记录。API key 只进入测试进程环境，没有写入代码或报告，
测试完成后持有密钥的进程已退出。

通过真实 `/models` 读取元数据，而非在测试适配器中写死窗口：

| 项目 | tokens |
| --- | ---: |
| 模型上下文窗口 | 1,048,576 |
| 服务端最大输出上限 | 393,216 |
| 默认策略预留输出 | 8,192 |
| 默认策略安全余量 | 2,048 |
| 默认有效输入上限 | 996,147 |
| 默认压缩触发点 | 943,718 |
| 默认压缩目标 | 707,789 |
| 优先保留近期历史 | 24,000 |

大输入场景只把输出上限降至 256，窗口与自动触发点保持模型推导值。
协议说明见 [模型元数据](https://api-docs.deepseek.com/api/list-models/) 和
[Chat Completions](https://api-docs.deepseek.com/api/create-chat-completion/)。

## 实测结果

| 场景 | 真实观察 | 结果 |
| --- | --- | --- |
| 超过旧 128K 窗口 | 22,000 条记录；服务端输入 154,111 tokens | 首、中、尾标记 3/3 正确；没有摘要调用 |
| 大输入 | 125,000 条记录；服务端输入 875,111 tokens，约物理窗口的 83.5% | 首、中、尾标记 3/3 正确；没有摘要调用 |
| 连续压缩 | 4 次真实摘要，7 次主模型请求，4 个完整工具轮次 | 24 项断言全部通过 |
| 裁剪后恢复 | 原始结果约 40,000 字符；活动投影限制 25,000 字符 | 模型一次搜索定位 sequence 4，再读取该条，找回中段 `CEDAR-7Q9` |
| 摘要截断，仍低于硬上限 | 摘要输出限制 32；服务端 `finish_reason=length` | 保留原上下文，不保存检查点 |
| 摘要截断，已超过硬上限 | 同样得到真实截断响应 | 拒绝准备下一次请求，不保存检查点，原始事件不变 |

连续压缩场景特意使用 32,768 的测试窗口、9,000 的触发点、7,500 的目标、
6,500 的近期历史预算，以便用少量真实调用覆盖多轮压缩。这些值没有改动默认策略。
摘要模型另用 65,536 的输入输出总窗口和 2,048 的输出预留。

复测保存的检查点如下。这里的数字是运行时预算计数，**不是**相应请求的服务端
实测输入；服务端用量另存于报告的 `requests`。

| 压缩到事件 sequence | 压缩前预算计数 | 压缩后预算计数 |
| --- | ---: | ---: |
| 4 | 15,061 | 7,708 |
| 8 | 15,682 | 7,776 |
| 12 | 15,762 | 7,857 |
| 16 | 9,790 | 1,860 |

前三次压缩后略高于 7,500 的目标，仍低于硬上限：目标是尽力达到的软目标，
保留最新完整轮次会占据空间。后续增长触发新的摘要，没有循环压缩同一个检查点。

最终 9 个字段全部正确，包括 `dry-run`、`eu-west-1`、250 ms、
保留公共 API 的要求、最早批次的 `ORBIT-42`、回滚标签、校验命令和回查得到的
归档值。用户原文在每次主请求中完整保留；独立读取事件存储也验证了原始工具
输出未被压缩或裁剪覆盖。

## 发现和修正

1. **搜索匹配了转义后的 JSON。** 原实现对序列化事件执行子串查询，包含引号、
   反斜杠或换行的原文会漏匹配。现在按事件原始字符串字段和事件类型匹配，
   保留工具名、调用 ID 查询，预览仍使用 JSON。回归测试覆盖这些字符、普通
   大小写不敏感搜索和元数据边界。
2. **搜索描述没有说明连续子串语义。** 首轮模型把多个关键词拼成查询，连续两次
   没命中，之后通过宽范围读取找到了答案。现在工具描述及参数说明明确了字面
   子串匹配。复测中一次查询直接命中原始工具结果；新增断言要求搜索真正找到
   对应事件，防止“调用过搜索就算通过”。
3. **测试提示的字段类型不明确。** 首轮模型返回 `batches: 4`，而断言要求
   `[1,2,3,4]`。提示现在明确要求整数数组，断言没有放宽；复测通过。首轮记录
   保留，不能将该格式差异描述成上下文信息丢失。

## 用量、证据和复现

包含连通性探测、首轮诊断、复测和大输入补测，共 29 次 Chat Completions 请求：
输入 1,372,058 tokens，输出 6,552 tokens；输入中 251,776 为缓存命中。
缓存数是输入的子集，没有从上下文容量扣除。以上是用量统计，不是费用估算。
没有网络或限流错误；两次 `length` 是有意制造的摘要失败。

- `results/deepseek-context-probe.json`：连通性探测。
- `results/deepseek-context-all.json`：首轮原始结果，包含字段类型失败和两次摘要截断。
- `results/deepseek-context-runtime.json`：修正描述与提示后的连续压缩复测，24/24。
- `results/deepseek-context-large.json`：154,111 和 875,111 输入场景，分别 8/8。

复现入口：`crates/agent-runtime/examples/deepseek_context.rs`。
先在环境中设置 `DEEPSEEK_API_KEY`，然后运行：

```sh
cargo run -p agent-runtime --example deepseek_context --locked -- all
```

当前 `all` 包括后来新增的大输入补测，因此会比保存的首轮 `all` 多一组场景。
代码与适配器范围详见 `crates/agent-runtime/examples/deepseek_context/README.md`。
普通测试不联网。

## 实际边界

本次采用非思考模式，没有验证思考内容回传、流式响应、服务端原生压缩、网络重试
和长时间任务可靠性。DeepSeek 思考模式要求在工具对话中完整回传
`reasoning_content`；本次文本适配器没有实现该路径，不能把测试通过推广到该模式。
参见 [官方思考模式要求](https://api-docs.deepseek.com/guides/thinking_mode/)。

计数也仍然是估算与真实用量校准的组合：大输入样本估算 881,367、实际 875,111，
但工具上下文的部分样本估算 8,163、实际 10,378。新请求、工具集合变化或压缩后
不能假定旧校准继续有效；当时建议接近硬上限时引入 provider tokenizer 或完善
超窗错误恢复。tokenizer 方向已于 2026-10-21 撤回，当前使用本地估算与正常
usage 校准，并保留压缩余量及超窗恢复；这里的实测数据未作改动。
这次大输入没有触及 943,718 的默认触发点，也没有证明任意内容在
1M 边界都能安全提交。
